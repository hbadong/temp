## 十、迭代规范

### 提交规范

```
feat: create game detail page template
fix: replace invalid cid placeholder
fix: add Swiper CSS via CDN
```

### 审查流程

每完成一个模板：自检 → 提交 → 对照审查清单 → 修复 → 重新提交

### Skill 自我迭代（实战沉淀机制）

skill 不是静态文档，而是与实战共同进化的知识库。**每次模板开发完成后**，把过程中遇到的非平凡问题、解决方案、核心沉淀、经验总结补充回本 skill，让后续项目复用——避免重复踩坑。

#### 触发时机

满足以下任一条件即触发自我迭代：

- 用户明确要求"补充完善该 skill"或"沉淀经验"
- 一次开发过程中遇到 ≥3 个新类别问题（不是重复问题）
- 发现现有沉淀规则有遗漏、错误或不够具体
- 新增了模板类型（之前未覆盖的页面种类，如专题页、聚合页）

#### 沉淀四要素

每次迭代必须包含以下 4 个层次（避免只描述现象而无方法）：

| 要素 | 内容 | 示例 |
|------|------|------|
| **遇到的问题** | 真实场景描述 + 触发条件 + 后果 | index.js 被 inc-header 与 inc-footer 重复引用 → 移动菜单 toggle 一次 add 一次 remove = 永远不动 |
| **解决方案** | 实际采用的修复方式 + 代码位置 | 从 inc-header.htm:12 移除 `<script src="index.js">`，只保留 footer 引用一次 |
| **核心沉淀** | 提炼为可复用的规则 / 检查项 | 沉淀为"### JS 交互陷阱"下的 #36："JS 双加载致命" |
| **经验总结** | 方法论层面的总结 | 核心原则：静态比对 ≠ 运行时正确。必须 curl 渲染 + node --check JS + 数据库字段对比三件套 |

#### 沉淀通用性红线（用户要求）

沉淀的每条经验必须**通用**——写给"任意目标网站的下一个复刻项目"，不针对某一个源网站模板：

| 要求 | 写法 |
|------|------|
| 规律优先 | 表述写**机制/规律/检查方法**，换一个目标网站仍然成立 |
| 示例中性 | 举例用中性描述（"详情页 tabs、侧栏浮动、轮播"），不绑定源站专名（域名、URL 路径、频道名） |
| 案例标注 | 确需源站具体案例佐证时，标注"实战案例"并保证规律句独立于案例成立 |
| 框架可具体 | LeCMS 框架机制（编译期文本替换、缓存层级、block 参数规则）是项目固定前提，**可以写具体**，不算站点特定 |
| 自检问题 | 写完自问："换一个完全不同的目标网站，这条还成立、还有用吗？"——不成立就不是沉淀，是站点备忘 |

#### 沉淀流程

```
1. 回顾开发过程：列出所有遇到的非平凡问题（不在现有核心沉淀内的）
2. 分类归入现有章节或新建子章节（按上表位置）
3. 提炼为表格条目：编号续接 + 标题 + 一句话说明（必要时附代码/示例）
4. 必要时附"何时使用"与"为什么"（不只是描述现象）
5. 更新 SKILL.md frontmatter description：
   - 核心沉淀总条数（45 → N）
   - 反映新内容（如"JS 双加载/toggle 类名/IIFE continue 等交互陷阱"）
6. 保留原有内容不动（避免破坏已有结构与编号连续性）
```

#### 质量标准

- 每条规则必须有真实问题对应（**实战验证**，非纸上谈兵）
- 说明必须包含"何时使用"和"为什么"
- 编号连续不跳号（如 #36-40 一组 #41-43 一组）
- 表格格式与现有风格一致（` | # | **标题** | 说明 | `）
- 代码示例用 fenced code block 标注语言

#### 反例（不应沉淀的内容）

| 类型 | 例子 | 为什么不沉淀 |
|------|------|------------|
| 项目特定的 CSS 数值 | `.compactShareButton{min-width:138px}` | 不同主题数值不同 |
| 一次性环境问题 | Windows 端口被占用重启 | 一次性，与模板无关 |
| 用户特殊需求 | logo 用 GD 生成 | 需求特定，非通用规则 |
| 重复内容 | 已有的"伪静态开启" | 已在 #19 |
| 工具使用技巧 | 用 PHP 比 sed 更可靠 | 已在 #32-35 |

#### 长期维护建议

- **每个项目结束时**：问"本次遇到了哪些 skill 没覆盖的问题？"
- **定期回顾**：每 3-6 个月检查核心沉淀条目是否过时（如 LeCMS 升级后 API 变化）
- **建立 issue 列表**：把发现的遗漏或错误记录下来，下个项目修复
- **避免过度沉淀**：每条规则必须 3 个项目复用验证后才"晋升"为核心沉淀
